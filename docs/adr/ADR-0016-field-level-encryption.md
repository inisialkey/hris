# ADR-0016: Field-Level Encryption for Sensitive Identity and Bank Data

Status: **Accepted** (grilled and ratified 2026-08-02, four amendments applied in-session) · Date: 2026-08-02 · Deciders: product owner + engineering (spec §5.13 mandates "field-level encryption for the most sensitive payroll/identity fields — ADR")

## Context

Spec §5.13 requires field-level encryption for the most sensitive fields on top of disk-level encryption at rest. The candidate fields live in employee master data (`docs/06-modules/employee.md`): NIK, NPWP, BPJS numbers, bank account details. UU PDP (27/2022) raises the stakes: these are national identifiers and financial data of employees, and erasure/breach obligations apply (security-standards §9). Constraints: `uq_employees_tenant_id_nik` needs equality/uniqueness over an encrypted value; payroll needs salary figures **computable** (aggregates, engine math, dashboards); RLS + repository scoping (ADR-0002) already isolate tenants.

## Decision

1. **Scope — encrypt identifiers and bank data, not amounts.**
   - Encrypted: `nik`, `npwp`, `bpjs_kesehatan_number`, `bpjs_ketenagakerjaan_number`, bank account number + holder name (exact column list finalized in `docs/06-modules/employee.md`).
   - **Not** field-encrypted: salary/component amounts — payroll math, reporting, and dashboards query them; protection is disk encryption + RLS + RBAC + audit log + PII-free telemetry. Encrypting amounts would push decryption into every aggregate and kill the reporting model for marginal gain.
   - Also **not** field-encrypted (grilling 2026-08-02): PTKP status (a category code the tax engine reads for every employee every run — near-zero identity value alone), birth date, address, phone (RBAC masking covers display; HR admin search legitimately uses them). Widening the encrypted set requires a superseding ADR.
2. **Mechanism — application-layer AEAD.** AES-256-GCM, random nonce, ciphertext stored as `text` (`v1:` version prefix + base64(nonce ‖ ciphertext ‖ tag)). Implemented as a Drizzle custom column type (`encryptedText`) so repositories encrypt/decrypt transparently; domain and API layers see plaintext strings, masked per RBAC rules at the presentation layer (employee.md defines masking).
3. **Searchability — blind index columns, NIK and NPWP only (grilling 2026-08-02).** Equality lookups and unique constraints run on a sibling column: `nik_bidx = HMAC-SHA256(tenant_index_key, normalize(nik))`, `normalize` = digits-only. `uq_employees_tenant_id_nik` becomes unique on `(tenant_id, nik_bidx)`; NPWP gets the same treatment with a partial unique (nullable — non-NPWP employees). BPJS numbers and bank fields are encrypted **without** indexes — no equality path exists in any documented flow; adding a bidx later is a backfill job, not a redesign. Exact-match only — no partial/like search on encrypted fields, by design; admin search uses name/employee number instead.
4. **Keys — envelope encryption, per tenant.** One KMS-held master KEK (cloud KMS, `asia-southeast2`, portable behind a `KeyProvider` port); per-tenant DEK + index key generated at provisioning, stored wrapped in a platform table, cached decrypted in-process with short TTL. Per-tenant DEKs give: blast-radius containment, per-tenant rotation, and **crypto-shredding** — destroying a tenant's DEK renders its ciphertext permanently unreadable (UU PDP erasure story for tenant offboarding, security-standards §9).
5. **Rotation.** KEK rotation = re-wrap DEKs (cheap, no data touched). DEK rotation = per-tenant `maintenance` re-encrypt job walking encrypted columns (version prefix identifies old material). Rotation cadence and triggers in security-standards §8.
6. **Where it does not apply.** Mobile Drift replicas never store these fields — profile APIs return masked values always. Self-view of own full values (employee verifying their bank account / NIK) is an explicit **reveal** action: online-only fetch, rendered from memory, never persisted to Drift, registered as a sensitive read (audit-log §4.3) — employee.md defines the endpoint and the per-role masking matrix (grilling 2026-08-02). Logs/traces/Sentry already ban these fields (ADR-0011 + redaction registry).
7. **Individual erasure (UU PDP) is purge-based, not key-based (grilling 2026-08-02).** A single employee's erasure request is lawfully refused while statutory payroll/tax retention runs; after the horizon, the existing purge jobs (database-conventions §4.4) hard-delete rows — ciphertext, blind indexes, and satellites included. Crypto-shredding stays a **tenant-offboarding** instrument only.

## Alternatives considered

- **pgcrypto in-database encryption.** Rejected: keys enter SQL text/server memory and every DBA/log path; app-layer AEAD keeps keys out of the database entirely.
- **Transparent disk encryption only.** Rejected by spec §5.13 (it demands field-level) — disk encryption does nothing against SQL-level exfiltration (injection, stolen credentials, misbehaving RLS bypass).
- **Deterministic encryption for searchability (AES-SIV).** Rejected: equality leakage across rows without a keyed index; HMAC blind index gives the same lookup with an independently rotatable key.
- **Encrypt salary amounts too.** Rejected: breaks aggregate queries, dashboard widgets, and payroll engine math; the residual risk on amounts is accepted and compensated (RLS, RBAC, audit, telemetry bans).
- **Per-field keys.** Rejected: key sprawl with no threat-model gain over per-tenant DEK + AEAD.
- **Per-employee DEKs (individual crypto-shredding).** Rejected: ~5M keys at the design ceiling (500 tenants × 10k employees), cache/rotation sprawl — for an erasure right that statutory retention already gates; purge jobs satisfy it after the horizon (decision 7).

## Tradeoffs

Encrypted columns cost ~2× storage and a per-row crypto hop on read — bounded: the fields are read on profile/payroll-setup paths, never in hot list queries (masked list views don't decrypt). Blind indexes leak equality within a tenant (same NIK ⇒ same digest) — acceptable: NIK is unique per tenant anyway. Losing the KEK or a DEK loses the plaintext irrecoverably — mitigated by KMS durability + wrapped-DEK backups alongside PITR; this is also the feature (crypto-shredding). In-process DEK cache is a memory-scraping surface — accepted for V1, same trust class as the DB credential.

## Consequences

- `docs/06-modules/employee.md` finalizes the encrypted-column list, masking rules, and ships `*_bidx` columns + uniques in its Drizzle schema; import/export (ADR-0015) validates NIK/NPWP against the blind index for duplicate detection.
- `docs/06-modules/employee.md` registers the reveal endpoints (self + admin) in the audit-log §4.3 sensitive-read registry.
- Provisioning (system-administration) generates DEK + index key per tenant; `KeyProvider` port lands in `shared/`… crypto helpers are platform code, whitelisted per ADR-0001. **Landed 2026-08-04:** the platform table this line left unnamed is **`tenant_keys`** (system-administration.md §4.1 — `wrapped_dek`, `wrapped_index_key`, `kek_version`, `dek_version`, one row per tenant, owned there by ADR-0001 rule 5 because provisioning is its only writer while the `shared/` crypto helper is its only reader). Generation runs **before** the provisioning transaction and is idempotent on tenant slug, so a KMS call never holds a database transaction open and a rolled-back provision leaves only unreferenced key material that the retry reuses. No API in that module deletes the row — deleting it *is* the crypto-shred, which decision 4 reserves for tenant offboarding and system-administration.md BR-ADM-009 keeps as a runbook procedure rather than an endpoint.
- security-standards §8 carries the operational rules (rotation, KMS reference, shredding procedure); backup-restore.md notes wrapped-DEK backup requirements. **Discharged 2026-08-04** — `backup-restore.md` §11 answers it in three parts. **The wrapped DEKs need no separate backup**: `tenant_keys` is an ordinary table, so they are *inside* PITR, and saying so matters because "back up the keys" is an instruction that invites an export, and an exported wrapped DEK plus KEK access is the entire plaintext. **A KEK version is never destroyed, only disabled** — destruction is irreversible and global across all 500 tenants, the destroy binding belongs to the human Terraform identity alone, and the crypto-shred destroys a **DEK, a database row**, never a KMS version. And the finding this ADR did not anticipate: **the crypto-shred is not complete when performed.** Every backup and every point inside the PITR window taken before it still contains the wrapped DEK, so a restore resurrects it — the erasure completes only when the last such backup expires, the procedure ends by recording that date, and whether an unreadable-but-restorable copy counts as erased carries a `⚠️ VERIFY`. Post-restore reconciliation re-executes any shred the restore crossed (§7.4).
- bpjs.md / tax-pph21.md exports decrypt at generation time inside worker jobs (never bulk-decrypt to intermediate storage).

## Future considerations

CMEK per tenant (ADR-0009 note) can join the same KeyProvider when contracts demand. If Postgres TDE or a managed field-encryption primitive matures on Cloud SQL, revisit mechanism, not scope. Searchable encryption (order-revealing, etc.) stays out — the exact-match boundary is deliberate.
